# AI-2A.3 operational and data-governance runbook

Production is NOT DEPLOYED. Keep `CLINICAL_AUDIO_ENABLED=false` for initial release. This task does not configure Hostinger, production secrets, migrations, patient processing, AI-3 or prescription reconciliation.

## Provider contracts verified on 2026-09-15

Synthetic live capture confirmed that unstored Gemini results may omit the interaction ID and emit zero-based `spk:0` labels. Both bounded colon and documented underscore labels are preserved verbatim; no request ID is invented. See the dedicated QA report for the observed contract and clinical-quality limitation.

Consulted configured local Sarvam MCP tools `sarvam_code_api_reference` for `/transliterate` and `/speech-to-text/job/init`, and `sarvam_code_languages`. MCP's STT reference still recommends v3 and its transliteration list includes 23 languages. The current endpoint documentation lists only English plus Hindi, Bengali, Gujarati, Kannada, Malayalam, Marathi, Odia, Punjabi, Tamil and Telugu. Preserve the already live-verified Saaras v4 Batch transport and MIME canonicalization. Use the narrower endpoint coverage; Urdu/Perso-Arabic and other unsupported scripts are not sent for transliteration.

- [Sarvam transliteration endpoint](https://docs.sarvam.ai/api-reference/text/transliterate-text): `POST https://api.sarvam.ai/transliterate`, `api-subscription-key` server-only header; JSON `input`, explicit supported `source_language_code`, `target_language_code=en-IN`, `numerals_format=international`, `spoken_form=false`. Maximum 1000 characters; response `transliterated_text` and `source_language_code`. Never call translation.
- [Gemini transcription](https://ai.google.dev/gemini-api/docs/transcribe) and [Interactions reference](https://ai.google.dev/api/interactions-api): `POST /v1beta/interactions`, `model=gemini-3.5-transcribe`, `store=false`, Files URI in an audio input. `generation_config.transcription_config.language_codes=[]`; `mode={type:verbatim, diarization_mode:speaker, timestamp_granularities:[word]}`. No smart mode or custom vocabulary. Strict `word_info` annotations in model-output text content; offsets in seconds, speaker labels, finite/duration-bounded timestamps, bounded body/text/counts. Consecutive same-speaker words become internal segments with punctuation-aware spacing. Require audio at most 30 minutes; up to eight speakers.
- [Gemini Files](https://ai.google.dev/gemini-api/docs/files): resumable start then streamed `upload, finalize`; poll file readiness within a bounded pass. Restrict returned upload destination and file URI to the official API origin. Explicit DELETE in `finally`, using a separate cleanup timeout; no public source URL, inline audio JSON, signed URLs in database or provider bodies in logs. Whole processing budget five minutes; file deletion 30 seconds. The dedicated transcription key is preferred; blank `GEMINI_TRANSCRIPTION_API_KEY` intentionally reuses server-only AI-1 `GEMINI_API_KEY`, without changing AI-1 behavior.

## Organization and clinician controls

Sarvam remains primary. `TRANSCRIPTION_AUTO_FALLBACK=false` is mandatory policy. Tenant opt-in defaults false and is managed on Settings → Features → Clinical AI with existing tenant-wide `feature:manage`; `feature:view` permits reading. Clinic-scoped admins cannot approve an organization-wide additional processor. Changes emit metadata-only enabled/disabled audit events.

Fallback requires a terminal technical Sarvam failure, READY retained audio, valid consent, live entitlement/permissions, assigned linked Doctor, valid Gemini configuration and duration at most 30 minutes. No fallback after an existing successful source transcript. Authentication and ownership are checked server-side. Clinician selects **Try Gemini** and explicitly confirms; generic retry remains Sarvam-only. The registration/recording/tenant locks, unique active key and permanent unique fallback key prevent duplicates. A fallback preserves the failed Sarvam run and creates its own run and immutable source. Ambiguous Gemini submission is not automatically repeated or switched to another provider.

Original transcript is the default. Romanization is a separately queued, source-hash-keyed segment view. Corrections never feed the derived view. Latin text passes through exactly without a provider call. Supported scripts use bounded sequential requests, at most three transient attempts with backoff, lossless grapheme-safe 1000-character partitioning and source-order reconstruction. Unsupported/failed segments retain original text, and the view is visibly partial. Derived clinical text is stored only in its dedicated tables, not generic audits, analytics or AiRun. Source bindings are guarded by foreign keys/triggers. A unique source/type key plus a locked creation transaction handles simultaneous requests; worker leases protect processing.

## Raw-audio retention

`RECORDING_AUDIO_RETENTION_DAYS` must be explicit, an integer from 1 to 3650 in enabled production. Zero-day retention is unsupported by this recording/transcription workflow and fails preflight. Completion into READY freezes `audioDeleteAfter` prospectively; changing the environment does not recalculate historical deadlines. Review any old READY rows without deadlines in a separately approved operation, never silently backfill them here.

Run `npm run clinical-audio:cleanup` persistently or `npm run clinical-audio:cleanup:once` on a supervised schedule. It claims one overdue READY recording with a database token/120-second lease. Uploads are excluded. Active transcription is guarded for at most 24 hours beyond retention; thereafter stuck jobs are terminally fenced and cleanup waits one full lease interval before deleting bytes. Storage deletion is bounded; missing objects are idempotent. Failed storage deletion leaves `audioDeletedAt` unset and schedules retry after 60 seconds. Mark deletion only after successful deletion/confirmed absence. Two workers cannot claim the same item simultaneously; optional tenant scoping is available for isolated operational/tests use.

Provider-file cleanup separately claims terminal Gemini runs with pending artifacts using the existing lease. It explicitly retries deletion, treats 404 as absence, and delays failure retry by 60 seconds. Immediate file deletion is primary; provider automatic expiry is only secondary. Application raw-audio deletion does not control Sarvam's copy.

After deletion, source, speaker mapping, corrections, review and Romanization remain available. Playback reports **Audio no longer retained**, timestamp clicks are safe, and server requests for either transcription provider are rejected. Existing bearer read URLs can remain usable until their short TTL expires; object deletion removes future access.

Configure the storage provider's incomplete multipart abort lifecycle before production. Use a narrow reviewed rule for the clinical-audio prefix, e.g. abort uploads after an approved one-day interval. Confirm no legitimate resumable-upload policy requires a longer interval. Record provider-side rule evidence; the application already aborts explicit discards/withdrawals. Do not assume an unconfigured bucket cleans up abandoned multipart uploads.

## Worker supervision and health

Set `CLINICAL_AUDIO_WORKER_MODE` to `persistent`, `scheduled-once` or `external` only after confirming the host actually supports that arrangement. Run `clinical-audio:worker` with a restart policy and injected server-only environment; it processes one durable transcription pass and one derived view at a time. SIGTERM/SIGINT stops subsequent work at safe boundaries. A lost transcription lease aborts provider use; durable checkpoints and fenced writes prevent stale completion. Interrupted leases expire after 120 seconds. Do not force-kill until the current bounded pass and file cleanup have had time to finish; allow a termination budget that covers provider requests (up to 120 seconds each), plus cleanup. Monitor oldest queued time, expired leases, runs past provider deadlines, Romanization queue, provider cleanup backlog and overdue retention using `npm run clinical-audio:health`. Logs contain metadata/status only.

Hostinger's managed Node.js hosting does not run a permanent worker and does not ship custom files written under `.next/server`; the earlier `node .next/server/clinical-audio/worker.mjs` cron failed with `MODULE_NOT_FOUND` on every run. On Hostinger use `CLINICAL_AUDIO_WORKER_MODE=external` with `CLINICAL_AUDIO_CRON_SECRET` and the HTTPS cron routes documented in `docs/clinical-ai-recording-transcription.md` (header file, never the secret in the cron command). Replace any cron entries that run `npm run clinical-audio:worker:once` or `clinical-audio:cleanup:once` inside `hbuilds/current`. The CLI scripts remain for local, VPS or external worker hosts. Persistent and cleanup processes should restart after failure; scheduled jobs should not overlap needlessly, though database leases fence overlap.

## Storage acceptance and configuration gates

Run `npm run clinical-audio:preflight` read-only, against the intended configuration/database. It checks feature state, real S3-compatible configuration, TLS, explicit retention, Sarvam key/model/polling, callback secret/HTTPS origin, explicit fallback policy, Gemini availability when opted-in tenants need it, worker declaration and migration status. Never print secrets. Disabled mode reports CONFIGURED BUT DISABLED; enabled production recording fails closed if core storage/retention/Sarvam/worker configuration is invalid. Gemini configuration failure only disables fallback; AI-1 and prescriptions retain their established gates.

`npm run clinical-audio:storage-acceptance` uses an 18 MiB synthetic silent WAV, three 8 MiB-or-smaller parts, private test prefix and finally cleanup. It verifies TLS, multipart/signed PUT/ETag, completion, exact HEAD MIME/bytes, actual SSE metadata, signed read/hash, browser audio-element playback, unauthenticated denial, expiry, delete/missing-object behavior and multipart abort. Set `CLINICAL_AUDIO_STORAGE_ACCEPTANCE_ORIGIN` to a narrow approved browser origin to check PUT CORS and ETag exposure. It checks bucket public-access blocking and policy status when the provider supports those APIs; unsupported APIs require independent evidence and produce a conditional result. Never log signed URLs. No vendor account/bucket is created. Missing real configuration is NOT RUN. Full acceptance requires the origin and bucket privacy checks as well as the object lifecycle checks.

## Patient-data governance prerequisites

Sarvam organization owner must record approved workspace/key, Dashboard → Settings → Workspace → Data retention, relevant API product override, training/data-use setting and approved retention period. Review current account controls directly; nothing here asserts those settings are configured.

Gemini requires an approved project/key, appropriate paid/data-processing arrangement, jurisdiction-specific organization approval, fallback-only purpose and explicit tenant opt-in. Never use free-tier patient/PHI data. Paid access or an API key is not compliance approval.

Storage requires approved raw-audio retention, encryption accepted by the intended provider, private bucket, public access blocked, least-privilege credentials, approved origins, multipart lifecycle, deletion monitoring and rollback evidence. Approval covers each processor's copy separately. No real patient text/audio was used for this milestone; live tests use synthetic input only.
